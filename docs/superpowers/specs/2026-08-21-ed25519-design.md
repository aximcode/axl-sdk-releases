# Ed25519 for AxlCrypto — vendored signatures, opt-in at link time

> **Status: E1 and E2a SHIPPED. E2b planned and PARKED 2026-08-23. E3-E5 not
> started.** Owner of the facts about *why mbedTLS cannot provide this*, why
> the 30 KB table must not land in every image, and how a second algorithm gets
> added later without a redesign.
>
> - **E1** — `AXL_CHECKSUM_SHA512` over mbedTLS, and `AxlHmac` widened to a
>   128-byte block. Measured 2,301 B (§10).
> - **E2a** — `AxlPkKey` is a tagged union behind the `AxlPkProvider` vtable,
>   ECDSA and RSA only, no behaviour change. Measured +8,976 B on a
>   verify/sign-only consumer (§10). §4b-bis records what reaching the seam
>   actually cost.
> - **E2b** — planned in full

>   than a working feature. Source is pinned at openssh-portable `V_10_5_P1`
>   (`b3f73442`) and the vectors are generated, so picking it up is cheap.
> - **§6b is the open question E4 inherits**, and it was found while grounding
>   E2b rather than while planning E4.
>

## 1. Summary

Ed25519 signing and verification as a real `AxlCrypto` capability, filling in
the `AXL_PK_ED25519` enum value that `axl-crypto.h` has carried as "reserved"
since it was written.

Three properties shape everything below:

1. **mbedTLS cannot supply the curve**, so the group and scalar arithmetic is
   vendored (§2). It *can* supply the hash, and after the `AXL_TLS` removal it
   does, in every build (§3).
2. **The fast implementation costs ~30 KB of resident `.rodata`**, and the SSH
   server is a resident firmware driver, so it must be **opt-in at link time**
   rather than present in every image (§4).
3. **Ed448, Ed25519ph/ctx and a leaner X25519 are wanted later**, so the seam
   is shaped for them now — retrofitting it after consumers exist is an API
   break (§5).

## 2. Why vendored — mbedTLS 3.6.3 has no Edwards curve

`axl-crypto.h` records the reason as "requires PSA crypto, which AXL does not
enable". **That is wrong, and it is worth correcting in the header**: enabling
PSA would not help, because there is nothing underneath it.

Verified against `deps/mbedtls` at 3.6.3:

| checked | result |
|---|---|
| `PSA_ALG_ED25519PH` | present in `include/psa/crypto_values.h` as a **constant only** |
| any `library/*.c` implementing EdDSA | **none** — the sole hit is `ssl_debug_helpers_generated.c`, a debug string table |
| `mbedtls_ecp_group_id` curves | SECP*/BP*/**CURVE25519**/CURVE448 — no `ED25519` |
| `MBEDTLS_ECP_TYPE_*` | `SHORT_WEIERSTRASS` and `MONTGOMERY` only — **no twisted Edwards** |

`MBEDTLS_ECP_DP_CURVE25519_ENABLED` is the **Montgomery** form, used for X25519
ECDH. Ed25519 needs the twisted Edwards form of the same curve, which is
different arithmetic mbedTLS does not implement.

**One thing mbedTLS does already have:** `MBEDTLS_SHA512_C` is enabled
(`src/net/axl-mbedtls-config.h:111`) and `library/sha512.c` compiles today —
now in **every** build, not only a TLS one. §3 uses it.

## 3. SHA-512 is mbedTLS's, surfaced through AxlDigest

Ed25519 is EdDSA over Curve25519 **with SHA-512**. `AxlDigest` today implements
its own MD5, SHA-1 and SHA-256 (`src/data/axl-digest-{md5,sha1,sha256}.c`), and
`axl-digest.c`'s file comment says *"Standalone — no mbedTLS dependency."*

**This section previously chose to hand-write a fourth sibling.** Its stated
reason was that depending on mbedTLS "would tie `AxlChecksum`, a base-library
module, to the TLS build toggle, which is the larger harm." **That toggle no
longer exists**, so the reason is void and the decision reverses.

**Decision: `AXL_CHECKSUM_SHA512` is a thin adapter over `mbedtls_sha512_*`.**
`src/data/axl-digest-sha512.c` implements the same
`sha512_init`/`update`/`final` prototypes the other three algorithms expose
through `axl-digest-internal.h`, so `axl-digest.c`'s four `switch` sites gain
one `case` each and nothing else changes shape.

### 3a. Why the layering objection is weaker than it reads

mbedTLS is confined to `src/net/` today — a grep over `src/` finds references
in that directory and nowhere else, so a new `AxlData → mbedTLS` edge looks
like an inversion. **It is not a new coupling, only a new direction.** mbedTLS
already depends *back* on the base modules through its platform shim:

| `axl-mbedtls-platform.o` needs | defined in |
|---|---|
| `axl_memset` | `src/data/axl-str.c` — **AxlData** |
| `axl_vformat` | `src/format/axl-format.c` |
| `axl_calloc_impl` / `axl_free_impl` | `src/mem/axl-mem.c` |
| `axl_log_full` | `src/log/axl-log-emit.c` |
| `axl_time_get_ms` / `axl_clock_gettime` | `src/util/axl-time.c` |

So AxlData and mbedTLS are already mutually referencing within one static
archive, which the linker resolves by rescanning. The boundary this section
was implicitly defending had already been crossed from the other side.

### 3b. What it costs, measured

x64 release, `size(1)` on the current tree — `text` includes `.rodata`:

| object | text | drags in |
|---|---:|---|
| mbedTLS `sha512.o` | **2,208 B** | only `mbedtls_platform_zeroize` — already AXL's own via `MBEDTLS_PLATFORM_ZEROIZE_ALT`, a 32 B object |
| `axl-digest-sha256.o` (our SHA-256, for scale) | 1,331 B | nothing |

A hand-written SHA-512 would land near 1.5-2 KB, so **size does not
discriminate between the two options.** What discriminates is that wrapping
writes no new cryptographic code — nothing for §8's security review to audit —
and duplicates nothing in any image.

**The cost that is real, and accepted deliberately:** `axl-digest.c` is a
`switch` dispatcher, so every `AxlChecksum` consumer strongly references every
algorithm and `--gc-sections` cannot separate them. Any image touching *any*
checksum therefore picks up 2,208 B of mbedTLS where today it picks up none.
That is ~7% of the 30,720 B `--minimal-runtime` floor, though a minimal image
uses no checksum at all. **Decided: accept it** rather than put SHA-512 behind
the §4 weak seam — that seam exists for 30 KB, and buying 2.2 KB with a second
opt-in flag plus a NULL-return failure mode a consumer can hit by surprise is a
bad trade. §10 records the number rather than leaving it as this estimate.

### 3c. Consequences worth stating plainly

- Ed25519's vendored code takes its hash from mbedTLS, so **a minimal-runtime
  app verifying a signature does link mbedTLS's `sha512.o`** — 2.2 KB, not the
  TLS stack. The previous section promised "no mbedTLS at all"; that promise is
  withdrawn, and it was never worth much, because §4's consumer is a resident
  SSH driver that links TLS regardless for X25519 and AES-256-GCM.
- One hardware kernel can now serve three consumers (§6). Hand-writing SHA-512
  would have needed two kernels to reach the same coverage.
- `sizeof(AxlChecksum)` grows for every consumer: the state union widens from
  `Sha256State` (104 B) to a SHA-512 context (~216 B), `MAX_DIGEST_LEN` 32 → 64
  and `MAX_HEX_LEN` 65 → 129. About +208 B per **heap object**, not per image.
  `AxlHmac` grows for the identical reason: `opad` 64 → 128 B (+64), `digest`
  32 → 64 B (+32), `hexstr` 65 → 129 B (+64), plus a new `size_t block` field
  (+8) now that the block size is per-algorithm rather than a hardcoded 64 —
  about **+168 B per HMAC context**, again per heap object, not per image.
- `AXL_CHECKSUM_SHA512 = 3` extends an enum whose numeric values `axl-digest.h`
  does not document as persisted contract (unlike `AxlPkAlgorithm`, which does).
  Appending is safe.

### 3d. Where the mbedTLS type is allowed to appear

`axl-digest.c` embeds each algorithm's state directly in a union inside
`AxlChecksum`, so `Sha512State` needs a concrete size at that point. Two ways,
and the choice is made here so E1's plan does not have to reopen it:

**Decided: `axl-digest-internal.h` includes `<mbedtls/sha512.h>` and defines
`Sha512State` as a struct wrapping a real `mbedtls_sha512_context`.** It is an
internal header (`"do not include from outside src/data/"`), so no mbedTLS type
reaches a public header and `check-uefi-scope`'s public-API rule is untouched.

The rejected alternative — an opaque `uint8_t raw[N]` with `N` hand-set to the
context size — is exactly the drift hazard this project keeps paying for: `N`
and mbedTLS's real `sizeof` are two facts that must agree, with nothing forcing
them to, and a submodule bump changes one of them silently. A
`static_assert` could catch it, but including the header removes the second
fact entirely.

## 4. The 30 KB problem, and the opt-in seam

### 4a. Why `--gc-sections` alone cannot solve it

`axl_pk_key_new` (`src/net/axl-pk-verify.c:314`) is an `if/else-if` dispatcher
that every `AxlPk` consumer calls. An Ed25519 branch inside it is a **strong
reference**, and `--gc-sections` collects at section granularity: retaining the
dispatcher retains everything it references, including the precomputed
base-point table.

That table is not small. ref10's `ge_precomp base[32][8]` is 32 x 8 x 120 bytes
= **30,720 bytes of `.rodata`**, resident forever in a firmware driver.

This is the same problem the log engine had, and it has the same answer.

### 4b. The seam, following `axl-log-dispatch.h`

`src/log/axl-log-dispatch.h` documents a solved instance: 682 emitter call
sites meant every image pulled the log engine, which is why `--minimal-runtime`
once measured ~0 bytes saved. The fix moved the decision to **one symbol**,
declared weak at the reference site and pulled with `-u`.

Applied here:

- `AxlPkProvider` — a vtable per algorithm: `keygen`, `sign`, `verify`,
  `public_export`, `public_import`.
- One weak symbol per provider, e.g. `_axl_pk_provider_ed25519`, declared weak
  and NULL-checked in `axl-pk-verify.c`, defined in `src/net/axl-pk-ed25519.c`.
- Opting in is `-u _axl_pk_provider_ed25519`, mirroring `$(LOG_ENGINE_PULL)`,
  plus an `axl-cc` flag. AxlSsh's driver link asks for it. Nothing else pays.
- Without it, `axl_pk_key_new(AXL_PK_ED25519)` returns NULL — **exactly what the
  header documents today**, so the failure mode is unchanged and fail-closed.

**The trap, quoted from the precedent because it is the easiest thing here to
get wrong:** the weak attribute must be applied *only where the reference is
made*. A `weak` attribute on a declaration in the translation unit that then
*defines* the symbol makes the **definition** weak, leaving it weak inside
`libaxl.a` and making `-u` unreliable. `axl-pk-verify.c` defines
`AXL_PK_PROVIDER_WEAK` before including the shared header; `axl-pk-ed25519.c`
does not. One prototype either way, so the two cannot drift.

### 4b-bis. What the seam costs to reach — read before planning E2

**Added 2026-08-21 after reading `axl-pk-verify.c`. §4b describes the END
state; this is the distance to it, which the section did not account for.**

`AxlPkKey` is not a tagged structure with an mbedTLS member. **It *is* an
mbedTLS context:**

```c
struct AxlPkKey {
    mbedtls_pk_context pk;
    AxlPkAlg           alg;
    bool               has_private;
};
```

Ed25519 cannot live in an `mbedtls_pk_context` — that is §2's whole finding.
So the seam requires turning this into a tagged union and dispatching before
every use: **24 sites touch `->pk`, across 14 public functions.** Three
consequences, each measured against the code rather than assumed:

- **`axl_pk_key_sign` hardcodes a pipeline EdDSA cannot use.** It computes a
  digest into `uint8_t hash[48]` and calls `mbedtls_pk_sign(pk, md, hash,
  hlen, …)`. Ed25519 (RFC 8032 §5.1) signs the **message**, not a digest —
  the hashing is internal and happens twice. The pre-hash step has to be
  bypassed, not parameterised.
- **`md_for_alg` is a silent wrong default, and it is the bug class E1 just
  removed.** `return (alg == AXL_PK_ECDSA_P384) ? MBEDTLS_MD_SHA384 :
  MBEDTLS_MD_SHA256;` — so `md_for_alg(AXL_PK_ED25519)` yields SHA-256 with
  no error. A ternary gets no `-Wswitch`. This is
  `axl_checksum_type_get_length`'s `default: return 0` in a different
  costume, and it is fixed as part of E2a.
- **There is no raw key import/export.** Only `from_ec_xy` / `get_ec_xy` /
  `from_rsa_ne` / `get_rsa_ne` and the DER pair. Ed25519 needs raw 32-byte in
  and out, which is what SSH uses natively. That is **new public API**, so it
  takes a contract-first review per CLAUDE.md workflow A.

**Decision (2026-08-21, with Mike): E2 splits.** E2a restructures `AxlPkKey`
into the tagged union and the provider seam carrying **only the existing
mbedTLS algorithms** — no new cryptography, so §8's review has nothing new to
audit and the existing ECDSA/RSA vectors prove it behaviour-preserving. E2b
then vendors ref10 behind a finished seam.

The reasoning is E1's, generalised: E1's safety property was provable
*because* the widening landed before the new algorithm existed, with the
existing tests as the net. Doing both at once asks one reviewer to audit
vendored curve arithmetic and a 14-function refactor of a shipped
security-sensitive file in a single diff.

### 4c. The gate

`check-ed25519-linkage`, appended to `LINT_GATES_ARTIFACT` beside
`check-log-linkage` (adding a gate is one edit — see CLAUDE.md). It asserts a
driver image that did **not** opt in carries zero ref10 bytes.

It ships with its own control in the same test: an image that **did** opt in
must show the table present. A gate whose silence has never been shown to be
capable of noise proves nothing.

## 5. Built to extend — the second axis

Two axes, so that later algorithms are additions rather than redesigns.

**Axis 1 — provider (which algorithm).** Adding Ed448 is: one provider object,
one enum value, one weak reference. No dispatcher surgery.

**Axis 2 — backend (which kernel).** Within a provider, a portable kernel and
optionally an accelerated one, chosen once from `axl_cpu_simd_tier()` /
`axl_cpu_features()`. `src/gfx/axl-gfx.c` is the working in-tree precedent.

Two shape decisions that must be made now because they are API:

- **`sign`/`verify` take a mode plus a context from day one**, even though v1
  implements only pure Ed25519 (RFC 8032 §5.1). Concretely: an `AxlPkSigMode`
  enum whose only v1 value is `AXL_PK_SIG_PURE`, and a `(const void *ctx, size_t
  ctx_len)` pair that v1 requires to be `(NULL, 0)` and rejects otherwise.
  Ed25519ph and Ed25519ctx are the *same curve and the same key* with a prehash
  and a domain-separation string, so with those present they become later enum
  values on an existing provider; without them they are an API break. Rejecting
  a non-empty context in v1 rather than ignoring it is what keeps the promise
  falsifiable — an ignored context silently produces signatures that verify
  under the wrong domain.
- **X25519 will reuse this mechanism** on the `AxlEcdh` surface rather than
  inventing a second pattern. It is **not** shipped here: mbedTLS already
  provides X25519 and a second provider would be the duplicate
  `check-libc-overlap` exists to catch. Its future purpose is ECDH for an image
  that wants to link none of mbedTLS's bignum/ECP machinery — note this is
  *smaller-image* motivation, not *no-TLS-build* motivation, since after the
  `AXL_TLS` removal every build has mbedTLS available.

## 6. Implementation choice

**Group and scalar layer: ref10** (SUPERCOP; the implementation OpenSSH itself
bundles), vendored in-tree at `deps/ed25519-ref10/`, public domain. Chosen on
provenance: this is security-gated firmware code and OpenSSH is the conformance
oracle for its first consumer.

**Field layer: two backends behind one internal interface.**

| backend | source | built for | selected when |
|---|---|---|---|
| portable | ref10's own limb arithmetic | both arches | always available; the fallback |
| ADX/BMI2 | fiat-crypto 64-bit field ops (MIT, **formally verified C**) compiled `-madx -mbmi2` | x64 only | `features.adx && features.bmi2` |

Choosing formally verified C over hand-written assembly is deliberate: GCC emits
`MULX`/`ADCX`/`ADOX` from `__uint128_t` arithmetic under `-madx -mbmi2`, so the
acceleration arrives without an unauditable assembly blob in code that §8 makes
a security gate.

### 6b. The field layer is NOT swappable in the source E2b vendors

**Found 2026-08-23 while grounding E2b, and it constrains E4 rather than E2b.**

This section assumed ref10's historical multi-file layout — `fe25519.c`,
`sc25519.c`, `ge25519.c` as separate translation units, where a field backend
is a link-time substitution. **OpenSSH no longer ships that.** As of
`V_10_5_P1` (commit `b3f73442`), `ed25519.c` is a single ~202 KB amalgamation
derived from `supercop-20221122`, and every field operation is `static` inside
it:

```
118:static void fe25519_add(fe25519 *r, const fe25519 *x, const fe25519 *y);
122:static void fe25519_mul(fe25519 *r, const fe25519 *x, const fe25519 *y);
```

Only three symbols are exported — `crypto_sign_ed25519`,
`crypto_sign_ed25519_open`, `crypto_sign_ed25519_keypair_from_seed` — which is
excellent for E2b (one file, one seam, nothing to namespace) and is exactly why
the vendoring is small. But it means **§6's "two backends behind one internal
interface" cannot be done by substitution.** E4 has three options and none is
free:

| option | cost |
|---|---|
| Patch the vendored file to make the field layer swappable | A local patch to vendored cryptographic code, which **must be disclosed** in `THIRD_PARTY.md` — the libvterm lesson, where eight undisclosed patches were an unmet obligation. It also makes every future OpenSSH resync a merge |
| Vendor the older multi-file ref10 instead | Weakens the reason the source was chosen: OpenSSH is AxlSsh's conformance oracle, and matching what it *currently* ships is the point |
| Drop the ADX backend | Loses nothing functional. §10 already notes the SSH workload is **one signature per connection**, so the acceleration was always for a load this project does not have |

**No decision is made here** — E2b needs only the portable path and is
unaffected. E4 makes the call with a measurement in hand, and the third option
should not be dismissed: it is the only one that costs nothing and it is
consistent with §10's own framing.

**SHA-512 backends — this is no longer a kernel we write.** mbedTLS 3.6.3
**already ships an aa64 `FEAT_SHA512` kernel** (`sha512h` / `sha512su0`
intrinsics in `library/sha512.c`, gated on
`MBEDTLS_SHA512_USE_A64_CRYPTO_IF_PRESENT`). What it does not ship is a way to
*detect* the feature on our target:

| mbedTLS detection path | needs | usable under UEFI |
|---|---|---|
| `getauxval(AT_HWCAP)` | Linux `sys/auxv.h` | no |
| `sysctlbyname` | Apple | no |
| `SIGILL` + `setjmp`/`longjmp` | `__unix__`, signals | no |

With none of them present, `sha512.c:196-203` emits `#warning "No mechanism to
detect A64_CRYPTO found, using C code only"` and **`#undef`s the acceleration**
— it compiles clean and silently does nothing. That is the exact failure
CLAUDE.md names as *"a gate that cannot see is worse than none"*, arriving from
a dependency rather than from us.

So the aa64 work is **supplying detection, not writing a kernel**, via
`MBEDTLS_SHA512_PROCESS_ALT` (still supported in 3.6.3 —
`sha512.c:294`, `sha512.c:592`): AXL defines `mbedtls_internal_sha512_process`,
dispatches once on `axl_cpu_features().sha512`, and calls either the hardware
path or mbedTLS's portable compressor. **One kernel then accelerates TLS
handshakes (SHA-384/512), Ed25519, and `AxlChecksum` together** — which the
hand-written design of §3 could not have done without two.

`MBEDTLS_SHA512_USE_A64_CRYPTO_ONLY` is rejected: it assumes every target CPU
has FEAT_SHA512, which a general UEFI image cannot. Patching the submodule to
add an AXL detection function is rejected too — `PROCESS_ALT` is the documented
extension point and keeps `deps/mbedtls` tracking upstream unmodified.

x86 gains little here — SHA-NI covers SHA-1/SHA-256 only, and the x86 SHA512
extension is confined to very recent parts — so no x86 SHA-512 kernel is built.

**One knob to decide with the measurement, not before it:**
`MBEDTLS_SHA512_SMALLER` is currently **on**
(`src/net/axl-mbedtls-config.h:113`), selecting the size-optimized, slower
compressor. Ed25519 hashes the message plus two more blocks per operation, so
this is a per-signature cost. Turning it off spends bytes that TLS also pays;
§10 measures both before anything changes.

### 6a. The ADX kernel needs a gate that can see it

`scripts/check-no-avx.py` detects by **encoding**, and already lists `mulx`,
`pdep`, `bzhi` and the rest of BMI1/BMI2 in `VEX_GPR_MNEMONICS`, with the
correct reasoning: they carry a VEX prefix, touch no YMM state, and so run
under UEFI with `CR4.OSXSAVE` clear. They are still reported — they `#UD` on a
CPU without BMI — and route through the per-symbol `AVX_GATED_SYMBOLS`
allowlist. So the BMI2 half of this kernel is allowlistable exactly like
`blend_row_over_avx2`, with a justification naming where the dispatch lives.

**`ADCX`/`ADOX` are legacy-encoded, not VEX, so the gate cannot see them at
all.** An ADX kernel reaching a CPU without ADX would `#UD` with no gate to
catch it. Extending `check-no-avx.py` to detect those two mnemonics and route
them through the same allowlist is **part of this work, not a follow-up** —
shipping an instruction class the gate is blind to is precisely the failure
CLAUDE.md names as "a gate that cannot see is worse than none".

## 7. Testing

Four layers, each independently falsifiable, every check sabotage-verified.

1. **SHA-512** — FIPS 180-4 known-answer vectors (empty, `"abc"`, the 896-bit
   message, a long repeat), asserted as exact hex against
   `axl_checksum_get_string`. **These stay even though §3 no longer writes the
   implementation:** they pin *our* contract — the enum value, the digest
   length, the streaming `update`/`final` split, the hex formatting — none of
   which mbedTLS's own self-test covers. A vector that only proves mbedTLS
   works proves nothing about the adapter, so at least one case must feed the
   data across **two** `axl_checksum_update` calls split mid-block.
2. **Ed25519 positive** — RFC 8032 §7.1 vectors: secret to public, and
   (message, key) to signature, including the 1023-byte case. Bytes specified
   by someone else, so passing is evidence about the RFC rather than about
   ourselves.
3. **Ed25519 negative — the security-relevant half.** A naive verifier passes
   every positive vector and is still broken. Pinned explicitly: a signature
   with **S >= L** must be refused (the canonical malleability hole),
   non-canonical and small-order public keys refused, a single-bit-flipped
   signature refused, a valid signature against the wrong message refused.
4. **The seam, both directions** — an image without `-u` gets NULL from
   `axl_pk_key_new(AXL_PK_ED25519)`; an image with it gets a working key. The
   second half is the control that stops the first passing against a build
   where Ed25519 simply does not exist.

**Both backends must actually be exercised, not merely present.** The dispatch
is forced both ways in test so the portable path is covered on an ADX-capable
host and the ADX path is covered where the vCPU exposes it; a kernel selected
only by luck of the host CPU is untested on the other machine. Both arches.

## 8. Security review is a gate

Same standing as AxlSsh's: network-reachable crypto in firmware with no OS
isolation beneath it. **No merge without an independent review** of the
vendored code's provenance, the canonical-S and small-order checks, the
constant-time properties of both field backends, and the dispatch that decides
between them.

## 9. Non-goals (v1)

- **No Ed448.** The seam supports it; nothing implements it here.
- **No Ed25519ph / Ed25519ctx.** The mode + context parameter exists from day
  one so they are a later flag, not an API break.
- **No X25519 provider.** mbedTLS already supplies X25519; see §5.
- **No batch verification.**
- **No OpenSSH private-key file parsing** — that is AxlSsh's concern. Note
  this is *not* the same as DER, which is in scope: see the RFC 8410 entry
  below.
- **RFC 8410 DER for Ed25519 is IN SCOPE** (decided 2026-08-21 with Mike; this
  was previously unstated rather than excluded). mbedTLS cannot parse an
  Ed25519 `PrivateKeyInfo`/`SubjectPublicKeyInfo` — OID `1.3.101.112`, since
  it has no Edwards curve — so `axl_pk_key_load_private` and its four
  siblings need hand-written encode/decode for this one algorithm. Chosen over
  rejecting Ed25519 at those entry points so the DER surface behaves uniformly
  across algorithms: a valid PKCS#8 Ed25519 file returning NULL from
  `axl_pk_key_load_private` is a surprise a consumer cannot debug from the
  outside. It lands in **E2b** with the rest of Ed25519, and §8's review covers
  it — hand-written ASN.1 over untrusted bytes is exactly what that gate is
  for.
- **No x86 SHA-512 kernel** — see §6.
- **No hand-written SHA-512** — §3 reversed; the adapter wraps mbedTLS.
- ~~No non-TLS exposure of `AXL_PK_ED25519`~~ — **struck.** This non-goal

## 11. Phasing

| phase | state | deliverable | done when |
|---|---|---|---|
| **E1** | **SHIPPED** | `AXL_CHECKSUM_SHA512` — an adapter over `mbedtls_sha512_*` behind the existing `axl-digest-internal.h` prototypes | FIPS 180-4 vectors pass, both arches, including a split-`update` case |
| **E2a** | **SHIPPED** | `AxlPkKey` becomes a tagged union behind the `AxlPkProvider` seam, carrying **only** ECDSA/RSA. `md_for_alg` fails closed. Raw key import/export added (contract-first reviewed) | existing ECDSA/RSA vectors unchanged — the phase adds no cryptography, so a changed vector means the refactor broke something |
| **E2b** | **PLANNED, PARKED** 2026-08-23 — zero code | ref10 vendored + RFC 8410 DER, behind the finished seam. Plan: `docs/superpowers/plans/2026-08-23-ed25519-e2b-ref10.md` | RFC 8032 positive and negative vectors pass |
| **E3** | not started | `check-ed25519-linkage` + the `check-no-avx.py` ADCX/ADOX extension | a non-opting driver measures zero added bytes; both gates proven able to fail |
| **E4** | not started; **ADX half is an open question, see §6b** | aa64 `FEAT_SHA512` **detection** via `MBEDTLS_SHA512_PROCESS_ALT`, and *if* §6b resolves for it, an ADX/BMI2 field backend | both dispatch paths forced and tested; §10 measured |
| **E5** | blocked on E2b | Consumed by AxlSsh — `AXL_PK_ED25519` host key | AxlSsh P1 Task 6 unblocked |

**E1 shrank when §3 reversed.** It was "write SHA-512, portable"; it is now
"surface SHA-512 that already compiles in every build". What did **not** shrink
is its test burden — the FIPS vectors and the split-`update` case are the whole
point of the phase (§7).

**E4 rescoped rather than shrank.** The aa64 kernel exists upstream; the work
is detection plus proving the dispatch actually engages, which is the harder
half and the one §6 shows a dependency getting wrong.

**E2 split into E2a and E2b** once §4b-bis established that `AxlPkKey` *is* an
`mbedtls_pk_context` and the seam is a 14-function refactor of a shipped
security file, not a vtable dropped beside it. E2a is a refactor under existing
test protection (CLAUDE.md bucket C); E2b is new cryptography under §8's review
gate. Keeping them apart is what lets that review look at curve arithmetic
without a refactor mixed into the same diff.

**Each phase gets its own implementation plan**, not one plan for all five. E1
is a self-contained hash addition; E2 is the vendoring and the seam; E4 is
performance work that must not be entangled with correctness work under review.

E1 and E2 are independently useful and independently reviewable — E1 completes
`AxlDigest` whether or not Ed25519 ever lands. E5 is the reason this exists:
AxlSsh P1 is blocked on it, and its Task 4 already advertises `ssh-ed25519` in
KEXINIT with nothing behind it.

## 12. Known-wrong things this corrects

Recorded because each misled a reader, and one of them misled this session:

- **`axl-crypto.h:86`** says Ed25519 "requires PSA crypto, which AXL does not
  enable". Enabling PSA would not help (§2). The comment is fixed as part of E2,
  in the same change that makes the enum value real.
- **`axl-crypto.h` still describes a build flag that no longer exists, and
  this section's own scope note undercounted it.** It named "seven comments"
  in `axl-crypto.h` alone — lines 7, 15, 60, 126, 188, 371, 458, with line 126
  documenting `axl_crypto_available()` as "True only when AXL was built with
  `AXL_TLS=1`", now unconditionally true — but an E1 recount found an
  **eighth** in that same header, line 557, so even the narrow count was
  stale before it shipped. And `axl-crypto.h` is not the only carrier: the
  dead flag also appears in `axl-jose.h` (2 mentions), `axl-tls.h` (2),
  `axl-scram.h` (1), `axl-service.h` (1), `axl-http-server.h` (1),
  `src/net/README.md`, `src/service/README.md`, `sdk/examples/jose-demo.c`,
  `tools/{fetch,rfbrowse,mkfixture}.c`, and user-facing error strings in
  `src/net/axl-http-{client,server}*.c` — several of which print advice
  telling a consumer to set a flag that no longer exists.

  **DONE 2026-08-23 (`86a58b06`)**, as its own change rather than folded into
  an Ed25519 phase. The final census: 46 bare `AXL_TLS` across 22 files, of
  which **8 were runtime strings** — the part that actually mattered, since a
  consumer whose `https://` failed was told to rebuild with a flag that cannot
  be set. Twelve references were deliberately **kept**: seven in the Makefile
  plus `build-prefix.sh`, `install.sh`, `check-libc-overlap.py` and two file
  comments, all past tense explaining why code is shaped as it is.
  `AXL_TLS_OK` / `_ERR` / `_WANT_MORE` / `_H` are unrelated identifiers and
  the raw grep's 192 hits over-count badly — the instinct in the original note
  to re-grep rather than trust a count was right, and so was distrusting the
  grep itself.

  **One thing the sweep found that is not prose:** `axl_tls_available()` and
  `axl_jose_available()` now unconditionally `return true`, so
  `if (!axl_tls_available())` in `axl-http-server.c` and its twin in
  `sdk/examples/jose-demo.c` are **dead branches**. Their docstrings now say
  the functions are tautologies and point at `axl_pk_alg_available()` for the
  question that can still answer no. Removing the guards is a separate call
  and was not made: one is an SDK example where the check teaches a consumer
  the right habit.
- **This spec's own §3 was wrong within a day of being written**, and its §6
  planned to write a kernel the dependency already ships. Both were found only
  by re-reading `deps/mbedtls` and `src/data/` rather than by re-reading the
  spec. The general shape — *a decision outlives the constraint that produced
  it* — is why §3 now states the reason it reversed, not merely the new
  conclusion.
- **`docs/superpowers/specs/2026-08-21-axl-ssh-design.md` §6** states that
  `AXL_PK_ED25519` and `AXL_AEAD_CHACHA20_POLY1305` are "exactly what a default
  `ssh(1)` negotiates" and that "the hard, dangerous part is done". Two of its
  four rows are wrong: Ed25519 does not exist, and OpenSSH's
  `chacha20-poly1305@openssh.com` is a different construction from the RFC 8439
  AEAD `AxlCrypto` exposes — it needs raw ChaCha20 with a two-key split and a
  separately encrypted length field, which `AxlCrypto` has no entry point for.
  That table is corrected when this lands; the cipher question is AxlSsh's to
  settle (`aes256-gcm@openssh.com`, its own documented fallback, is supported
  today and enabled by default in OpenSSH 9.9p1).
