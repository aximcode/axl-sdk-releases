## 1. Summary

A tool over `AxlAcpi`, and the library work it needs.

The obvious half is a table browser: list what the firmware publishes, validate
checksums, decode the tables we have typed readers for, hexdump the rest. That
is worth building and it is most of the code.

**The half that motivates it is a discrepancy finder.** SMBIOS Type 9 (System
Slots), SMBIOS Type 41 (Onboard Devices Extended), the ACPI namespace
(`_SUN`/`_UID`/`_PLD` under a `Device` with an `_ADR`), and the PCIe Slot
Capabilities block in config space all claim to describe the same physical
slots — and on real hardware they disagree. That disagreement is a live source
of problems, and no existing tool can see more than one source at a time.

`lsacpi` is the only place that can see all four, which is why the correlation
belongs here rather than in `lspci`.

## 2. The four sources, and why they drift apart

| source | what it gives | how it goes wrong |
|---|---|---|
| **SMBIOS Type 9** | `designation` ("PCIe Slot 3"), `slot_type`, width, `current_usage`, and `segment_group`/`bus`/`device_function` | Populated by hand in the vendor's build. Stale after a board respin; `0xFFFF`/`0xFF` sentinels when a field was never filled in |
| **SMBIOS Type 41** | `reference_designation`, device type + instance, and its own `segment_group`/`bus`/`device_function` | Describes *onboard* devices, so it overlaps Type 9 where a device is soldered near a slot. Two hand-maintained tables, two chances to drift |
| **ACPI namespace** | `_SUN` (slot user number), `_UID`, `_PLD` (physical location), bound to a device by `_ADR` | Generated by a different part of the firmware build than SMBIOS. `_ADR` encodes only device+function — segment and bus come from the enclosing hierarchy. **How much it contributes varies wildly by machine:** one measured client published no `_SUN` at all and hid 85% of `_PLD` behind Methods, while a measured server published 26 static `_SUN` and every `_ADR` statically (§5a, §8b) |
| **PCIe Slot Capabilities** | Physical Slot Number, hot-plug capability, and — in Slot **Status** — Presence Detect | The hardware's own answer, and the only one that is not a build-time string. Meaningful **only** on a downstream port with Slot Implemented set |

The last row is the useful anchor: Presence Detect is ground truth about whether
something is in the slot right now, and Physical Slot Number is what the silicon
was strapped or programmed to report. Everything else is somebody's build-time
assertion about the board.

**The tool's job is to put all four in one row per device and mark where they
disagree.** It does not adjudicate — it reports, because which source is right
is a per-platform question the operator answers, not the tool.

## 3. What already exists — most of it

Checked against the tree rather than assumed. The premise that this needs "API
updates" turned out to be mostly wrong:

| need | status |
|---|---|
| Table discovery, iteration, checksum | `axl_acpi_next` / `_find` / `_find_next` / `_checksum_ok` |
| ECAM windows | `axl_acpi_read_mcfg` → `AxlAcpiMcfgEntry` (base, segment, bus range) |
| MADT, FADT | `axl_acpi_read_madt`, `axl_acpi_read_facp` |
| SMBIOS Type 9, with seg/bus/dev/func **and** sentinels | `axl_smbios_read_system_slot` → `AxlSmbiosSystemSlot` |
| SMBIOS Type 41, same fields | `axl_smbios_read_onboard_device_ext` → `AxlSmbiosOnboardDeviceExt` |
| PCI enumeration, config space, capability walk | `AxlPci`, `axl_pci_cap_next`, `axl_pci_ecap_next` |
| Hexdump | `AxlHexdump` |

Two things do not exist, and they are §5 and §6.

**A detail worth knowing before writing the tool:** `axl_acpi_next`'s catalog is
not just the XSDT. `build_catalog` follows the FADT's `X_Dsdt`/`Dsdt` **and**
`X_FirmwareCtrl`/`FirmwareCtrl`, front-loading FACS and DSDT in what the code
calls "oracle order". So DSDT is enumerable — but **FACS has no standard ACPI
header.** Its first 8 bytes are signature and length; offset 8 onward is
`HardwareSignature`, not revision/checksum/OEM. A tool that renders every
catalog entry through `AxlAcpiHeader` prints four columns of garbage and a
meaningless checksum verdict for exactly one row.

## 4. The scope boundary this revises

`axl-acpi.h:25` and `src/acpi/README.md:21` both say:

> Scope is discovery + typed readers; **AML interpretation is out of scope**
> (that's ACPICA-sized and not what diagnostic tools need).

That is right about *interpretation* and too broad as written. The distinction
that matters:

- **Executing** AML means a bytecode VM with `OperationRegion` access — on real
  hardware, an interpreter that touches SystemMemory, SystemIO and PCI config.
  That is ACPICA-sized and stays out of scope, permanently.
- **Parsing** static `Name()` declarations to find `_ADR`, `_SUN`, `_UID` and
  `_PLD` is a structural walk over a byte stream. No evaluation, no side
  effects, no hardware access.

**Decision: the scope statement becomes "no AML *execution*."** §5 builds the
parser; `_DSM` and every other Method stays unreadable and is reported as such.

### 4a. Why this is not a slippery slope

The parser has a hard stop that is easy to state and easy to review: **it never
evaluates.** A `Method` body is skipped by length, never entered. Anything whose
value is not a literal in the byte stream is reported as present-but-unreadable.
That is a property a reviewer can check by grepping for the absence of an
evaluation loop, not a judgement call about how much AML is too much.

## 5. The AML namespace walker

New: `src/acpi/axl-acpi-aml.c`, declared in `include/axl/axl-acpi.h`.

### 5a. It is feasible — but the VM fixture badly overstates how much is static

Measured twice: against `test/fixtures/proxmox-vm/acpi/dsdt.dat` (19,404 bytes,
present locally but untracked -- see §8), and against a **real-hardware capture** — an Intel Meteor
Lake-H mini-PC, AMI firmware, DSDT 446,170 bytes plus 21 SSDTs, 84,863 lines
decompiled. Both with `iasl`.

| object | VM: Name | VM: Method | real HW: Name | real HW: Method |
|---|---:|---:|---:|---:|
| `_ADR` | 131 | 0 | 183 | **96** |
| `_SUN` | **123** | 0 | **0** | **0** |
| `_UID` | 10 | 0 | 169 | 12 |
| `_HID` | 17 | 0 | 182 | 36 |
| `_PLD` | 0 | 0 | 11 | **61** |
| `_SEG` | 0 | 0 | **1** | 0 |
| `_BBN` | 0 | 0 | **0** | **2** |
| `_CRS` | — | — | 5 | **129** |
| `_DSM` | 0 | 123 | 0 | 176 |
| `_STA` | — | — | 8 | 193 |

**The earlier claim — "the static walker reads 100% of `_SUN` and `_ADR`" — was
true of the VM and does not generalize.** Three corrections follow, and they are
the reason this section was rewritten:

- **`_SUN` is absent entirely on the real machine**, in both forms. Stated
  fairly: that box is a mini-PC with no user-serviceable slots, and `_SUN` is a
  *slot* user number, so its absence is legitimate rather than a firmware bug —
  this does **not** show that servers lack `_SUN`. What it does show is that the
  VM's 123/123 is a QEMU artifact, and that **"no `_SUN` anywhere" is a normal
  case the tool must degrade through, not an edge case.** §7's output must not
  be built around a column that is empty on a whole class of machines.
- **34% of `_ADR` is behind a Method** (96 of 279). `_ADR` is the join key for
  the entire correlation, so a static walker silently misses a third of the
  bindings. The old table never counted `Method(_ADR)` — it only checked that
  `Method(_SUN)` was zero.
- **85% of `_PLD` is behind a Method** (61 of 72). §2 lists `_PLD` as one of the
  namespace's contributions; on real firmware it is mostly unreadable without
  execution, and the spec should promise no more than the 15% that is static.

None of this changes the feasibility verdict — a static walk still reads the
majority of `_ADR` and every `_SEG` — but it changes what the tool may claim.
Coverage is now a thing `lsacpi` **reports per object** (`static` /
`present-but-unreadable` / `absent`), not a thing the spec asserts up front.

**A third machine then made that rule non-negotiable.** §8b measures a Dell
PowerEdge server whose profile is the *opposite* of the mini-PC's on almost
every row — every `_ADR` static, 26 `_SUN`, but every `_SEG` and `_BBN` behind
a Method across 17 root bridges. Three captures, three distributions, no two
alike. Do not read the table above as "how firmware looks"; read it as "how
one machine looked".

### 5b. The parser's actual requirement is skipping, not parsing

Devices in that fixture look like:

```
Device (S08) {
    Name (_ADR, 0x00010000)
    OperationRegion (P40C, PCI_Config, 0x60, 0x04)
    Scope (\_SB) { Field (PCI0.S08.P40C, ByteAcc, NoLock, Preserve) { … } }
}
```

So the walker must **skip what it does not understand by trusting PkgLength**,
never fail on it. `OperationRegion`, `Field`, `Method` bodies, nested `Scope` —
all stepped over. That skip-don't-fail property *is* the parser; the recognition
half is small by comparison.

It handles: `ScopeOp` (0x10), `DeviceOp` (0x5B 0x82), `NameOp` (0x08), and the
data opcodes a `Name` can carry — `ZeroOp`, `OneOp`, `OnesOp`, `BytePrefix`,
`WordPrefix`, `DWordPrefix`, `QWordPrefix`, `StringPrefix`, `BufferOp`,
`PackageOp`. Plus NameString encoding: root/parent prefixes, dual and multi
name prefixes, `NullName`.

**Hostile input is the norm here, not the exception.** The DSDT comes from
firmware, and a malformed or truncated table must produce a bounded walk that
stops, not a runaway or a read past the table. Every PkgLength is validated
against the remaining table length before it is trusted; nesting depth is
capped.

**Devices declared inside `If` are a real case the VM fixture does not have.**
On the real-hardware capture roughly 92 of 396 `Device(...)` declarations sit
inside an `If` block. The second host bridge is one of them:

```
Scope (_SB) {
    If ((PCHA != Zero)) {
        Device (PC02) {
            Name (_HID, EisaId ("PNP0A08"))
            Name (_SEG, Zero)
            Method (_BBN, 0, NotSerialized) { Return (PBSB) }
        }
    }
}
```

The condition is only knowable by evaluating AML, so a static walker cannot
decide whether `PC02` exists. Both available behaviours are wrong in one
direction: **skipping `If` bodies** loses ~23% of devices, **entering them**
reports devices that may not be present at runtime.

**Decision: enter `If`/`Else` bodies and mark everything found inside as
`conditional`.** The walker reports the device with a flag rather than
pretending to know; `lsacpi` renders it distinctly, and the correlation treats a
conditional device that config space does not confirm as *explained*, not as a
discrepancy. This keeps recall high while never asserting presence the walker
cannot establish — and it is consistent with §4a, since recognising `IfOp` and
stepping into its body is structural, not evaluative. The condition expression
itself is skipped by length and never parsed.

### 5c. The API — a cursor, matching the module's own idiom

`axl-acpi.h` already advertises *"Cursor-style iteration matches the SMBIOS
module"*, so the walker follows it:

```c
typedef enum {
    AXL_ACPI_AML_ABSENT = 0,   ///< the object is not present under this device
    AXL_ACPI_AML_VALUE,        ///< a static Name(); the value is populated
    AXL_ACPI_AML_METHOD        ///< present, but a Method — NOT evaluatable here
} AxlAcpiAmlKind;

typedef struct {
    char            path[64];       ///< namespace path, e.g. "\\_SB.PCI0.S08"
    uint32_t        adr;            ///< _ADR: bits 31:16 device, 15:0 function
    AxlAcpiAmlKind  adr_kind;
    uint64_t        sun;            ///< _SUN slot user number
    AxlAcpiAmlKind  sun_kind;
    uint64_t        uid;            ///< _UID
    AxlAcpiAmlKind  uid_kind;
    uint8_t         pld[20];        ///< _PLD revision-2 buffer, raw
    AxlAcpiAmlKind  pld_kind;
    AxlAcpiAmlKind  dsm_kind;       ///< always ABSENT or METHOD; never VALUE
} AxlAcpiAmlDevice;

/**
 * @brief Iterate Device() nodes in the ACPI namespace.
 *
 * Walks DSDT and every SSDT. Pass NULL to start. Returns false when
 * the walk is complete. Parses only static Name() declarations — no
 * AML is executed, so a Method-valued object reports
 * #AXL_ACPI_AML_METHOD rather than a value. Absent and unreadable are
 * deliberately distinct: they are opposite facts about the firmware.
 */
bool
axl_acpi_aml_next_device(
    AxlAcpiAmlDevice *cursor   ///< [in/out] zeroed to start; advanced in place
);
```

The library learns nothing about PCI. `_ADR` carries device and function only —
segment and bus come from the enclosing hierarchy (`_SEG`/`_BBN`, absent in this
fixture), so **mapping a namespace device to a PCI address is the tool's job**,
and the tool is honest when the mapping is ambiguous.

## 6. `axl_pci_read_slot_caps()`

New in `include/axl/axl-pci.h` / `src/pci/axl-pci.c`. Covers the **whole** PCIe
Slot block, not just Capabilities:

```c
typedef struct {
    uint16_t physical_slot_num;      ///< Slot Capabilities bits 31:19
    uint32_t slot_power_limit_mw;    ///< decoded from value + scale
    bool     hotplug_capable, hotplug_surprise;
    bool     power_controller, attention_button, mrl_sensor;
    bool     attention_indicator, power_indicator;
    bool     electromech_interlock, no_command_completed;
    /* Slot Status — runtime, and the only non-build-time truth here. */
    bool     presence_detect;        ///< something IS in the slot
    bool     mrl_open, power_fault, electromech_interlock_engaged;
    bool     has_vsec, has_dvsec;    ///< vendor caps present in extended space
} AxlPciSlotCaps;

int axl_pci_read_slot_caps(AxlPciAddr addr, AxlPciSlotCaps *out);
```

**It returns `AXL_ERR` unless the function is a Root Port or Downstream Switch
Port *and* the Slot Implemented bit (PCIe Capabilities Register bit 8) is set.**
Without that gate the register reads as reserved zeroes and a naive tool reports
"Physical Slot 0, no hot-plug" for every endpoint in the machine — confidently
and wrongly. Fail-closed means a caller cannot print a slot that does not exist.

`has_vsec` / `has_dvsec` come from `axl_pci_ecap_next` (extended IDs `0x000B`
and `0x0023`). The tool reports their *presence*, not their contents: vendor
capability layouts are per-vendor and decoding them is not something this tool
can do correctly for hardware it has never seen.

## 7. `lsacpi`'s output

Default is the table inventory, one row per table — signature, length, revision,
OEM ID, OEM table ID, **checksum OK/BAD**. FACS renders signature and length
with `-` elsewhere, per §3.

`lsacpi <SIG>` decodes through the typed reader where one exists (MCFG shows the
ECAM windows; APIC the interrupt controllers; FACP the fixed-feature pointers)
and **falls back to an `xxd`-style hexdump automatically** where one does not.
A tool that reports "DSDT, 19404 bytes" and stops is useless for the ~20 tables
with no reader, and requiring a flag to see bytes is friction in exactly the
case where you already know something is wrong.

**The correlation runs by default**, appended to the inventory whenever any of
the four sources yields something — no flag needed, because a mismatch nobody
asked to see is a mismatch nobody finds. `--no-slots` suppresses it for the
table-browsing case, and `--slots` shows *only* it.

Columns come from all four sources with a marker where they disagree.
Disagreement is the product; agreement is the boring case. **The row shape —
per slot or per device — is deliberately not settled here**; §12 records why.

**No column may be load-bearing, and no join path may be either.** §8a found
both its disagreements on a machine publishing **no `_SUN` at all**; §8b found a
server where `_SUN` is the only join for 74% of its slots and every `_SEG` and
`_BBN` is a Method. Two real machines, opposite profiles. So every namespace
column renders as one of *value* / *present-but-unreadable* (a Method) /
*absent*; the correlation degrades to whichever sources exist rather than
requiring four; and each row records **which join path produced it** — address
(§11b) or slot number (§8b) — because a row joined by slot number has not
verified a PCI address and must not imply one. A resolved PCI address
additionally shows whether its root bus was **confirmed or assumed**, per §11c.

`-v` verbose and `-j` JSON follow `lsproto`, the newest `ls*` tool. The name
follows `lspci`/`lsusb`/`lsproto`; `acpidump` was rejected because it carries a
hard expectation from Linux of raw table dumps consumable by `iasl`, which a
`--raw` flag can offer later without the name over-promising.

## 8. Testing, and what cannot be tested here

**The oracle is `iasl`, which is on the build host** alongside `acpidump` and
`acpixtract`. Every walker assertion is checked against `iasl -d` output on the
same fixture — an independent implementation, the same discipline the Ed25519
vectors got from two independent crypto libraries.

**Fixtures are LOCAL-ONLY, and that is a policy decision already made.**
`.gitignore:50` ignores `test/fixtures/` with its reason stated inline —
*"Hardware-fixture captures (HF1+) — machine-specific, often contain identifying
data (serials, MACs, OEM strings). Local-only by default; sanitization + public
corpus is HF10's scope."* A second rule ignores `DellXE7745/` as *"Real-hardware
capture data (not for distribution)."*

So `test/fixtures/proxmox-vm/acpi/dsdt.dat` is **not in the repository** — it is
an untracked local file, and `git ls-files test/fixtures` returns nothing. An
earlier draft of this section called it an "in-tree fixture, already present";
that was wrong, and it also explains why nothing reads it.

**Three captures exist locally** and L2 is graded against all three:

| location | source | what only it has |
|---|---|---|
| `test/fixtures/proxmox-vm/acpi/` | QEMU | the easy case: everything static |
| `test/fixtures/real-hw/client/` | Intel Meteor Lake-H, AMI | 96 `Method(_ADR)`, 61 `Method(_PLD)`, `If`-wrapped devices |
| `test/fixtures/real-hw/server/` | Dell PowerEdge XE7745, AMD | 26 `_SUN`, 17 root bridges, 17 `Method(_SEG)`/`_BBN`, 2 ECAM segments, 2.1 MB DSDT |

**The consequence for testing is structural, not incidental:** CI and every
fresh clone have **none** of them. Fixture-backed tests must therefore SKIP
cleanly and audibly when the capture is absent, with SKIP-path balancers per
`feedback_balancer_count` — never fail, and never silently pass. The synthetic
byte-array fixtures compiled into the unit tests are what runs everywhere; the
captures are the deeper local grading.

> **Capture hygiene:** an ACPI dump includes **MSDM, which carries the OEM
> Windows product key.** Any captured set must drop it. Worth a line in
> `mkfixture` rather than a rule people remember — even for a local-only
> capture, since HF10's public-corpus work will start from these.

**Hostile-input tests are mandatory, not optional.** Truncated tables, a
PkgLength that overruns the table, unterminated packages, deep nesting. The
walk must stop bounded in every case. These are synthetic and need no hardware.

**What is real-hardware-only, stated plainly rather than claimed:**

- ~~`axl_pci_read_slot_caps()`'s populated path~~ — **ANSWERED 2026-08-28 by
  L1, and it is CI-testable.** The QEMU runner already added a `pcie-root-port`
  on both arches for an unrelated regression test, so the success path needed no
  new harness: it reports `exp=0x0142` (Device/Port Type 4, Slot Implemented
  set) and `slotcap=0x0002007b`. **But only half the block is testable there.**
  Slot Capabilities discriminates well — bits 5 and 6 are adjacent and both set,
  so an off-by-one shift fails, proven by sabotage. **Slot *Status* is
  `0x0000`**, every bit clear, even though the port's secondary bus is
  populated: QEMU does not report Presence Detect for a cold-plugged device. So
  Slot Status bit positions **cannot be verified under QEMU at all** — with all
  bits zero the data cannot distinguish bit 5 from bit 6, and an assertion would
  pass against a wrong shift. That half is real-hardware-only and carries an
  explicit SKIP rather than a green assertion.
- SMBIOS Type 9 / Type 41 correlation — QEMU is unlikely to publish either.
- `_PLD` decode — absent from the VM fixture, and 85% Method on real hardware,
  so only the static minority is ever testable.

**The mismatch itself is no longer unproven.** This section previously said the
tool's value could not be demonstrated without real firmware. It has now been
demonstrated — see §8a — and the result is stronger than the spec assumed.

### 8a. The disagreement, measured on real firmware

Same machine as §5a. All four sources read independently, 2026-08-28.

| source | what it reported |
|---|---|
| SMBIOS Type 9 | **2** slots |
| SMBIOS Type 41 | **25** onboard devices |
| Slot Capabilities | **10** ports with Slot Implemented — Physical Slot Numbers 2, 3, 4, 5, 7, 8, 12, 13, 14, 15 |
| ACPI namespace | **nothing** — `_SUN` absent in both forms |

Two independent disagreements fell out, and they corroborate each other:

**"PEG SLOT X8"** — Type 9 slot ID **12**, Bus Address `0000:00:01.0`, Current
Usage *Available*.

- Config space enumerates 36 devices; bus 0 runs `00:00.0` → `00:02.0`. **There
  is no `0000:00:01.0`.** SMBIOS asserts a slot at an address that does not
  exist.
- Silicon's **Slot #12 is `00:07.1`**, a Thunderbolt port with no relationship
  to a PEG x8 slot. So the two sources' slot numbers collide on unrelated
  hardware.

**"PCIe SLOT X1"** — Type 9 slot ID **1**, Bus Address `0000:00:1c.0`, Current
Usage **In Use**.

- `00:1c.0` exists, and its Slot Capabilities says **Slot #2**, not 1.
- Its Slot Status says **PresDet−**, and `LnkSta: Width x0` — link down, nothing
  in the slot. Contrast `00:1c.3`, which reads PresDet+ / `Width x1, 5GT/s`.
- So SMBIOS claims the slot is occupied; **the hardware's own presence signal
  says it is empty**, and the slot numbers disagree by one.

This is exactly the class of drift §2 predicted, it is invisible to any single
existing tool, and — as §8 argued — **it is impossible to reproduce in the VM
fixture**, whose sources are generated consistently by one project. The tool's
premise is now evidence rather than argument.

### 8b. A second real machine — a server — inverts half of 8a

Measured 2026-08-28 on a **Dell PowerEdge XE7745** (AMD, Dell firmware, DSDT
**2,137,364 bytes** + 6 SSDTs, 262,260 lines decompiled). Deliberately a
different vendor, architecture and class from §5a's Intel/AMI mini-PC — and
the two disagree about which parts of the namespace are readable:

| object | mini-PC Name / Method | **server** Name / Method |
|---|---|---|
| `_ADR` | 183 / **96** | **434 / 0** |
| `_SUN` | **0 / 0** | **26 / 0** |
| `_UID` | 169 / 12 | 1057 / 0 |
| `_PLD` | 11 / 61 | **0 / 24** |
| `_SEG` | **1 / 0** | **0 / 17** |
| `_BBN` | 0 / 2 | **0 / 17** |
| `_CRS` | 5 / 129 | 7 / 30 |

**The lesson is that neither machine generalizes.** The mini-PC has a third of
`_ADR` behind Methods and no `_SUN`; the server has **every** `_ADR` static and
26 `_SUN`s, but **every** `_SEG` and `_BBN` behind a Method, across **17 root
bridges**. §5a's rule — report coverage per object, never assert it — is what
survives both.

**§11a's finding generalizes, and that is the important part.** On the server
`Method(_BBN)` returns `B002`, an 8-bit field inside
`OperationRegion (DPCI, SystemMemory, 0x3E992000, 0x1010)` — the *same shape*
as the mini-PC's `PBSB` in `GNVS`, from a different vendor on a different
architecture. Two independent firmware lineages put the bus number behind an
OperationRegion read. This is a pattern, not an anecdote.

**Root bridges are not findable by `_HID` here.** `_HID` and `_CID` are Methods
returning packed EISA dwords (`0x080AD041` = PNP0A08), so the literal string
never appears in the table. A walker that identifies host bridges by matching
`"PNP0A08"` finds **zero** on this machine. `Name(_UID, 0x00…0x10)` *is* static
on all 17, and is the only static handle they carry.

**§11c's ambiguity is real, not hypothetical.** MCFG publishes **2** ECAM
segments (`0x60000000` and `0x70000000`, each covering buses 0x00–0xFF), and
`lspci` confirms both segments are populated. 17 root bridges, 2 segments,
neither `_SEG` nor `_BBN` statically readable: **a namespace root cannot be
resolved to a segment or a bus base without evaluating AML.** The single-bridge
case §11c called "overwhelmingly common" is the *client* case, not the server
case.

#### The finding that changes the join

Across the server's **34** Type 9 records, verified against raw `dmidecode`
output rather than inferred:

- **25 carry a slot `ID` and NO `Bus Address`** ("PCIe Slot 23", `ID: 23`).
- **8 carry both.**
- **1 carries a `Bus Address` and no slot `ID`.**

> **Corrected 2026-08-28 by parsing the raw records.** An earlier reading of
> this said "9 carry a Bus Address and NO slot ID" and concluded the two halves
> are almost never in the same record. That came from `dmidecode`'s *rendering*,
> which omits the `ID:` line for M.2 socket types — not from the data. Parsing
> the Type 9 structures directly shows 8 records carry both. A list from
> observed output is not a census.

**The conclusion is unchanged, and it rests on the other half of the split:
74% of the records carry no address at all**, so joining purely on PCI address —
which is what §11b enables — cannot reach 25 of this machine's 34 slots however
good the resolution is.

The other 25 are reachable, and **`_SUN` is what reaches them.** Silicon
publishes Physical Slot Numbers **1–9 and 21–36** (plus ten high-numbered
internal ports: 160, 161, 194, 195, 201, 204, 228, 229, 390, 391), Type 9's IDs
cover 1–9 and 21–36, and the namespace's 26 `_SUN`s fall in the same range.
Three sources, one shared numbering, no bus number required.

**So §8a's conclusion was drawn from one machine and is corrected here.** It
said "the correlation must not be built around `_SUN`" — true of a mini-PC that
publishes none, false of a server where `_SUN` is the only join for 74% of its
slots. The correct rule is **two join paths, neither privileged**:

1. **By PCI address**, where both sides publish one (§11b resolves the
   namespace side).
2. **By slot number** — `_SUN` ↔ Type 9 `ID` ↔ Slot Capabilities Physical Slot
   Number — where they do not.

A row may be joined by either; the tool reports which path it used, because a
row joined by slot number has not verified its PCI address and must not imply
it has. And the counts already disagree — 34 Type 9, 36 Slot-Implemented ports,
26 `_SUN` — which is the product, not a problem.

## 9. Non-goals

- **No AML execution, ever.** `_DSM` and every Method reports `AXL_ACPI_AML_METHOD`.
- **No `OperationRegion` access.** The parser reads a table in memory; it touches
  no hardware.
- **No vendor capability decoding.** VSEC/DVSEC presence only.
- **No adjudication.** The tool shows disagreement; it does not decide who wins.
- **No `lspci` changes in this phase.** Slot columns there were discussed and are
  a reasonable follow-up, but the correlation needs all four sources and `lspci`
  has no reason to grow an AML walker. Revisit once `lsacpi` has run on real
  hardware.
- **No writes.** Read-only, always.

## 10. Phasing

| phase | deliverable | done when |
|---|---|---|
| **L1** | `axl_pci_read_slot_caps()` | reads a downstream port correctly; returns `AXL_ERR` for endpoints and for Slot-Implemented-clear, proven by test |
| **L2** | The AML namespace walker | counts match `iasl` on **both** fixtures — VM (131 `_ADR`, 123 `_SUN`) and real HW (183 `Name(_ADR)` + 96 `Method(_ADR)`, 0 `_SUN`, 2 `Method(_BBN)`, `If`-wrapped devices flagged conditional); hostile inputs terminate bounded |
| **L3** | `lsacpi` — inventory, checksums, typed decode, auto-hexdump | table list matches `acpidump` on the same machine; FACS renders without garbage |
| **L4** | The correlation view | sources present in one row, each column marked value / unreadable / absent; disagreement marked; sentinels honoured; root bus marked confirmed-or-assumed |

L1 and L2 are independent and either can go first. L3 depends on neither — it
is the table browser and is useful alone. L4 needs all three.

**L2 must be graded on the real-hardware fixture, not the VM one.** The VM has
zero `Method(_ADR)`, zero `If`-wrapped devices and one table; passing against it
alone would leave the hard half of the walker unexercised (§8).

## 11. Namespace → PCI address: settled

This was the design's weakest point. It has been settled against a real DSDT,
and the answer is **not** either of the two options previously floated.

### 11a. Both floated fallbacks are dead on real firmware

The old text proposed "assume segment 0 and derive bus from the host bridge's
`_CRS`", with "report the `_ADR` and let the operator judge" as the fallback.
Measured on the real capture, the first is not merely awkward — it is
unavailable:

- **`_BBN` is a Method, always.** 0 `Name`, 2 `Method`. The primary host bridge
  `PC00` has `Method (_BBN) { Return (BN00 ()) }` — a method calling another
  method. The secondary, `PC02`, has `Method (_BBN) { Return (PBSB) }`, and
  **`PBSB` is an 8-bit field inside `OperationRegion (GNVS, SystemMemory,
  0x65DCC000, 0x0DA5)`.** Reading it needs AML execution *and* OperationRegion
  access — the two hardest non-goals in §9, together, for one integer.
- **`_CRS` is 96% Methods** (129 vs 5), so the `_CRS` route fails for the same
  reason.
- **`_SEG` appears exactly once** in the whole namespace, on `PC02`. `PC00`, the
  bridge that actually matters, does not declare one.

An earlier draft would have specified a mechanism that cannot run.

### 11b. The answer: AML supplies topology, config space supplies bus numbers

The walker never needed `_BBN`. The two halves of a PCI address come from
different places, and only one of them is in AML:

- **AML gives the tree and device:function.** `_ADR` at each level encodes
  device and function, and the namespace path gives parent/child structure —
  both static, both already parsed by §5.
- **Config space gives every bus number.** MCFG already decodes to ECAM windows
  per segment with bus ranges (`axl_acpi_read_mcfg`, shipped), and each bridge's
  **Secondary Bus Number** register is a plain config-space read that `AxlPci`
  already performs.

So `\_SB.PC00.RP05.PXSX` resolves by descent: start at the root bus for `PC00`,
take `_ADR` of `RP05` for device:function on that bus, read **that bridge's**
Secondary Bus Number from config space, and recurse into `PXSX`. No `_BBN`, no
`_CRS`, no evaluation — and it composes from two subsystems the tree already
has.

This is strictly better than the old proposal: it is more accurate (the
hardware's own bus assignment rather than a firmware assertion about it) *and*
it stays inside §9's boundary rather than straining against it.

### 11c. The residual ambiguity, and how it is reported

One thing config space cannot supply: **which root bus a namespace root maps to
when there is more than one host bridge.** Here `PC00` (`_UID` 0, no `_SEG`) and
`PC02` (`_UID` 2, `_SEG` 0, and conditional under `If (PCHA != Zero)`).

- **One host bridge** — the *client* case: unambiguous, root bus 0.
- **Several** — the *server* case, and §8b measures how bad it gets: **17 root
  bridges across 2 ECAM segments, with every `_SEG` and every `_BBN` behind a
  Method.** Nothing static resolves them. `Name(_UID, 0x00…0x10)` is the only
  static handle they carry, and a `_UID` is not a segment or a bus number —
  treating it as one would be a guess wearing a measurement's clothes.

So on a multi-root-bridge machine the namespace side of the **address** join is
unavailable, and the tool says so rather than inventing a bus. That is not a
dead end, because §8b establishes a second join path: **slot number**
(`_SUN` ↔ Type 9 `ID` ↔ Physical Slot Number) needs no bus number at all, and
on the measured server it reaches 25 of 34 slots that the address join cannot.
Every row records which path joined it.

That is the right behaviour for a discrepancy finder specifically: it already
exists to surface where sources disagree, so surfacing its own unverifiable
assumption is the same contract, not a special case. A resolved address carries
whether its root bus was **confirmed** or **assumed**.
