# Ed25519 E1 — SHA-512 in AxlDigest Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add `AXL_CHECKSUM_SHA512` to AxlDigest as a thin adapter over
mbedTLS's `mbedtls_sha512_*`, and make `AxlHmac` safe and correct for a
128-byte-block, 64-byte-digest algorithm.

**Architecture:** `axl-digest.c` is a `switch` dispatcher over per-algorithm
`init`/`update`/`final` prototypes declared in the internal header
`src/data/axl-digest-internal.h`. SHA-512 joins as a fourth sibling whose
implementation forwards to mbedTLS rather than computing anything itself.
`AxlHmac` sits on top of that dispatcher and currently hardcodes a 64-byte
block and a 32-byte maximum digest; it is widened **before** the new enum value
exists, so no commit in this plan ever contains a tree where
`axl_hmac_new(AXL_CHECKSUM_SHA512, …)` can overflow.

**Tech Stack:** C (C11, `-Wall -Wextra`, gcc + clang-tidy), mbedTLS 3.6.3
(vendored submodule at `deps/mbedtls`, compiled unconditionally), QEMU-hosted
UEFI unit tests under `test/unit/`, `test/integration/test-axl.sh`.

**Spec:** `docs/superpowers/specs/2026-08-21-ed25519-design.md` — §3 (why the
implementation wraps mbedTLS rather than being hand-written), §3d (where the
mbedTLS type may appear), §7 item 1 (what the tests must pin), §11 (E1's place
in the phasing).

### The trap the compiler will NOT catch

`axl_checksum_update`, `checksum_finalize` and `axl_checksum_reset` each
`switch` on `cs->type` with **no `default:` label**, so adding an enum value
makes gcc's `-Wswitch` name all three sites. **`axl_checksum_type_get_length`
has a `default: return 0`, so it will not warn.** Forgetting that one is silent
and fails closed in the most confusing possible way: `axl_checksum_new` rejects
the type as invalid and every SHA-512 test returns NULL. Add that case first.

### Task order is a safety property, not a preference

Task 3 introduces the enum value. Until then `axl_hmac_new`'s only guard is
`axl_checksum_type_get_length(type) == 0`, which starts *accepting* SHA-512 the
moment the value exists. Tasks 1 and 2 remove the overflow and the over-read
**before** that happens, and Task 2's fail-closed `hmac_block_size` default
keeps HMAC-SHA-512 returning NULL until Task 4 deliberately enables it. Every
commit in this plan is safe on its own.

### Task 1: `get_digest` reports bytes written — in both AxlChecksum and AxlHmac

**Files:**
- Modify: `src/data/axl-digest.c:155-170`
- Modify: `include/axl/axl-digest.h:96-108` (the contract wording)
- Modify: `src/data/axl-hmac.c:155-167`
- Modify: `include/axl/axl-hmac.h:101-110` (the contract wording)
- Test: `test/unit/axl-test-data.c`

**Interfaces:**
- Consumes: nothing from earlier tasks.
- Produces: `axl_checksum_get_digest(AxlChecksum *cs, uint8_t *buf, size_t *len)`
  and `axl_hmac_get_digest(AxlHmac *h, uint8_t *buf, size_t *len)` — on return
  `*len` is **the number of bytes written into `buf`**, which is
  `min(entry *len, digest length)`. Tasks 2 and 4 rely on the AxlChecksum one.

**Both APIs carry the same defect and are fixed together.** `axl-hmac.h:107-108`
documents it outright — *"If the buffer is smaller than the digest, only `*len`
bytes are written but `*len` still reports the full digest length."* Fixing
`AxlChecksum` while leaving its twin documenting the identical hazard would ship
half a fix, and the two functions are read side by side.

**One ambiguity this creates in `axl_hmac_get_digest`, stated rather than
discovered later:** `*len == 0` is already the OOM-failure sentinel. Under
written-byte semantics a *successful* call with a zero-size buffer also reports
0. A zero-size buffer is degenerate and no in-tree caller passes one, so the
sentinel keeps its meaning in every real case — but the docstring must say so
explicitly rather than leave a reader to infer it.

**Why this is a real defect and not a refactor.** Today the function clamps the
*copy* to the caller's buffer but then reports the **full** digest length:

```c
size_t dlen = axl_checksum_type_get_length(cs->type);
if (*len < dlen) {
    dlen = *len;                                   /* clamp the copy */
}
axl_memcpy(buf, cs->digest, dlen);
*len = axl_checksum_type_get_length(cs->type);     /* …but report the full length */
```

A caller that passes a short buffer gets back a length larger than what was
written. `src/data/axl-hmac.c:64` does exactly that pattern with
`uint8_t idig[32]` and then calls `axl_checksum_update(outer, idig, ilen)` —
harmless only because no current algorithm exceeds 32 bytes. It is the
mechanism that turns Task 3's enum addition into a stack over-read, so it is
fixed first and separately.

**Every in-tree caller passes an exactly-sized buffer**, so this change is
invisible to all of them — verified: `axl-digest.c:237` (guarded
`out_len >= dlen`), `axl-hmac.c:64,69,104`, `axl-ssh-kex.c:168,188`
(`block[AXL_SSH_HASH_LEN]`, and it already asserts `blen != sizeof block`),
`axl-sys.c:415` (`digest[20]` for SHA-1), `axl-test-data.c:12061`.

```c
test_checksum_get_digest_short_buffer(void)

       many bytes it actually received. Reporting the full digest
       length while writing fewer bytes invites the caller to read
       past its own buffer -- which is exactly what axl-hmac.c did. */
    AxlChecksum *cs = axl_checksum_new(AXL_CHECKSUM_SHA256);
    test_check(cs != NULL, "get_digest short: new sha256");
    if (cs == NULL) {
        return;
    }

    uint8_t buf[8];
    size_t  len = sizeof(buf);
```

- [ ] **Step 3: Fix the length semantics**

In `src/data/axl-digest.c`, replace the body of `axl_checksum_get_digest`
(lines 155-170) with:

```c
void
axl_checksum_get_digest(AxlChecksum *cs, uint8_t *buf, size_t *len)
{
    if (cs == NULL || buf == NULL || len == NULL) {
        return;
    }

    checksum_finalize(cs);

    size_t dlen = axl_checksum_type_get_length(cs->type);
    if (*len < dlen) {
        dlen = *len;
    }
    axl_memcpy(buf, cs->digest, dlen);
    /* Report what was WRITTEN, not what the algorithm produces. A
       caller that passed a short buffer and got back the full digest
       length would happily read past its own array -- axl-hmac.c did,
       and it only stayed harmless while no algorithm exceeded 32
       bytes. Use axl_checksum_type_get_length() to size a buffer
       before the call. */
    *len = dlen;
}
```

- [ ] **Step 4: Fix the same defect in `axl_hmac_get_digest`**

```c
void
axl_hmac_get_digest(AxlHmac *h, uint8_t *buf, size_t *len)
{
    if (h == NULL || buf == NULL || len == NULL) {
        return;
    }
    hmac_finalize(h);

    size_t n = (*len < h->digest_len) ? *len : h->digest_len;
    axl_memcpy(buf, h->digest, n);
    /* Report what was WRITTEN -- same reasoning as
       axl_checksum_get_digest(). Note *len == 0 remains the
       failed-finalize signal: a successful call with a zero-size
       buffer also reports 0, which is degenerate and which no caller
       does. */
    *len = n;
}
```

### Task 2: Widen `AxlHmac` off its hardcoded 64-byte block

**Files:**
- Modify: `src/data/axl-hmac.c` (macros at 17-18, struct at 20-28, `hmac_finalize` at 44-77, `axl_hmac_new` at 81-133)
- Test: `test/unit/axl-test-data.c`

**Interfaces:**
- Consumes: `axl_checksum_get_digest`'s written-bytes semantics from Task 1.
- Produces: `static size_t hmac_block_size(AxlChecksumType type)` returning 64
  for MD5/SHA-1/SHA-256 and **0** for anything else; `axl_hmac_new` returns
  NULL when it is 0. Task 4 adds the SHA-512 case returning 128.

**What is wrong today.** `HMAC_BLOCK` is `64` and `HMAC_MAX_DIGEST` is `32`,
both hardcoded, and `axl_hmac_new`'s only algorithm guard is
`axl_checksum_type_get_length(type) == 0`. When SHA-512 enters the enum that
guard starts passing and `hmac_finalize` writes `hexstr[0..128]` into a
`char hexstr[65]` — a 64-byte heap overflow — while `axl_checksum_update(outer,
h->opad, 64)` silently computes a wrong MAC because SHA-512's block is 128.

This task fixes the shape **while only three algorithms exist**, so it is
provably behaviour-preserving: the RFC 4231 vectors below must produce
identical results before and after.

- [ ] **Step 1: Write the failing test**

```c
test_hmac_rfc4231_sha256(void)
{
    /* RFC 4231 HMAC-SHA-256 vectors. These pass today; they are here
       so that widening the block/digest handling is provably
       behaviour-preserving for the algorithms that already worked. */
    static const uint8_t k20[20] = {
        0x0b, 0x0b, 0x0b, 0x0b, 0x0b, 0x0b, 0x0b, 0x0b, 0x0b, 0x0b,
        0x0b, 0x0b, 0x0b, 0x0b, 0x0b, 0x0b, 0x0b, 0x0b, 0x0b, 0x0b
    };
    char *mac = axl_compute_hmac(AXL_CHECKSUM_SHA256, k20, sizeof(k20),
                                 "Hi There", 8);
    test_check(mac != NULL && axl_strcmp(mac,
        "b0344c61d8db38535ca8afceaf0bf12b881dc200c9833da726e9376c2e32cff7") == 0,
        "hmac rfc4231 sha256: TC1");
    axl_free(mac);

    mac = axl_compute_hmac(AXL_CHECKSUM_SHA256, "Jefe", 4,
                           "what do ya want for nothing?", 28);
    test_check(mac != NULL && axl_strcmp(mac,
        "5bdcc146bf60754e6a042426089575c75a003f089d2739839dec58b964ec3843") == 0,
        "hmac rfc4231 sha256: TC2");
    axl_free(mac);

    /* TC6 -- a 131-byte key exceeds the 64-byte block and must be
       hashed down first (RFC 2104). This is the path that a
       per-algorithm block size changes, so it must be pinned. */
    uint8_t k131[131];
    axl_memset(k131, 0xaa, sizeof(k131));
    mac = axl_compute_hmac(AXL_CHECKSUM_SHA256, k131, sizeof(k131),
```

```c
/** @file axl-digest-sha512.c
    SHA-512 (FIPS 180-4) for the AXL digest subsystem.

    Unlike its MD5 / SHA-1 / SHA-256 siblings this file computes
    nothing: it forwards to mbedTLS, which compiles into every build
    since the AXL_TLS flag was removed. See
    docs/superpowers/specs/2026-08-21-ed25519-design.md §3 for why
    wrapping beats a fourth hand-written compressor -- briefly, the
    two cost the same bytes and only one of them adds cryptographic
    code that a security review has to audit.

    The mbedtls_sha512_* calls each return int. This file discards
    those returns because the AxlChecksum API it implements has no
    error channel on update: axl_checksum_update() returns void. That
    is sound only while the underlying compressor cannot fail, which
    is true for MBEDTLS_SHA512_C with no *_ALT hook. E4 of the spec
    introduces MBEDTLS_SHA512_PROCESS_ALT; if that path can fail, the
    error must be plumbed through AxlChecksum rather than dropped
    here.
**/

#include "axl-digest-internal.h"

void
sha512_init(Sha512State *s)
{
    mbedtls_sha512_init(&s->ctx);
    mbedtls_sha512_starts(&s->ctx, 0);  /* 0 = SHA-512, 1 would be SHA-384 */
}

void
sha512_update(Sha512State *s, const uint8_t *data, size_t len)
{
    mbedtls_sha512_update(&s->ctx, data, len);
}

void
sha512_final(Sha512State *s, uint8_t out[64])
{
    mbedtls_sha512_finish(&s->ctx, out);
    /* Scrubs the context; the caller may re-arm it with sha512_init()
       via axl_checksum_reset(), which mbedtls_sha512_init() supports
       on a freed context. */
    mbedtls_sha512_free(&s->ctx);
}
```

## After E1

E1 is done when both arches are green, `verify.sh` is all green, the docs build
warning-free, and the review pass is applied. The spec's §11 puts **E2**
(ref10 vendored behind the weak provider seam) next; it does not depend on
anything in this plan beyond `AXL_CHECKSUM_SHA512` existing.

**Two things E1 deliberately does not do**, both recorded in the spec so they
are not rediscovered as surprises:

- **No `MBEDTLS_SHA512_PROCESS_ALT` work.** The aa64 `FEAT_SHA512` kernel
  already exists inside mbedTLS; what it lacks is detection that works under
  UEFI. That is E4, and §6 explains why mbedTLS's own `IF_PRESENT` path
  silently disables itself on a bare-metal target.
- **No `MBEDTLS_SHA512_SMALLER` change.** It is on today, selecting the
  size-optimized, slower compressor. §10 measures both arms before anyone
  touches it, because the byte cost lands on TLS as well.

**Unrelated but adjacent, and tracked in the spec's §12:** `axl-crypto.h` still
describes an `AXL_TLS=1` build requirement in seven comments (lines 7, 15, 60,
126, 188, 371, 458). Task 4 fixes the one instance in `axl-hmac.h` because that
file is already being edited; the `axl-crypto.h` sweep is its own change and
must not be folded in here.
